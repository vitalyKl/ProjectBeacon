# ТЗ 2 — Фаза research с узкими исследователями и структурированными находками

Формат — как в `ProjectBeacon-fix-plan.md`. Шаг 2 использует `CodeIndex.HashRange` из
`ProjectBeacon-tz-code-semantics.md` (Шаг 3); Шаг 5 использует `GetSignatures`/`GetCallers`
оттуда же (Шаги 1–2). Эти шаги можно делать в любом порядке относительно того ТЗ,
кроме прямых зависимостей, указанных в каждом шаге ниже.

## Контекст

Проверено по коду на момент написания:

- Дефолтный `TaskKind` — три фазы: `understand` (→ Planner) → `do` (→ Actor) → `check` (→ Review).
  `TaskPhase.FanOut: bool` существует, но дефолтным kind'ом не используется — `understand` это
  один агент, который сам исследует и сам планирует, без разделения.
- `Subtask.Summary` существует и пишется по завершении, но читается только в
  `SessionPrompts.Review` (строка «Summary: {sub.Summary}») — для финального ревью,
  не для передачи между рабочими подзадачами.
- `SessionPrompts.Actor` намеренно изолирует подзадачу от соседей
  («you are not told the surrounding task») — это осознанный выбор, не недосмотр.
- `task_create_subtask` (`CreateSubtaskHandler`) не ограничен ролью вызывающего на уровне
  хендлера — единственное условие: задача в стадии `Planning` или `Executing`. Технически
  уже вызываем любой подзадачей, у которой этот тул в `AllowedMcpTools`. Ограничения на
  количество или глубину такого порождения — нет.
- `GetTree` (через `CodeIndex`) уже возвращает `Size` на файл — можно оценивать объём
  зоны без чтения содержимого.

## Принципы неразрушения

1. Фазы `do`/`check` и их текущее поведение не переписываются — `research` добавляется
   как новая фаза перед ними, существующие задачи без неё работают как раньше.
2. Изоляция актёров друг от друга внутри фазы `do` не снимается целиком — открывается
   только чтение находок из фазы `research`, явным отдельным путём.
3. `Subtask.Summary` не удаляется и не переиспользуется под структурированные находки —
   это разные вещи: `Summary` человекочитаемый для Review, находки — машиночитаемые
   с цитатами для следующих фаз. Новое поле — отдельное.
4. `CreateSubtaskHandler` не получает ролевых проверок в этом ТЗ — ограничение количества
   делается отдельным, явным счётчиком (Шаг 4), не ломает существующий путь вызова.

## Шаг 1 — фаза `research` с fan-out

**Проблема.** Нет дефолтной фазы, которая бы расходилась на несколько узких
исследователей до планирования.

**Не трогать:** фазы `do`/`check`, их обработчики в `PipelineActorHandlers.cs`.

**Меняем.**
- В `TaskKindHandlers.cs` (строки с `("understand", ...)`, `("do", ...)`, `("check", ...)`) —
  добавить `("research", "Investigate the codebase", FanOut: true)` перед `understand`.
  `understand` остаётся как есть — синтез плана на основе находок `research`, не их замена.
- `ISessionSpawner.cs` — добавить явный маппинг роли на фазу `research` (сейчас там
  маппинг для `Planner`/`Review`/остальных на `understand`/`check`/`do`; `research`-фаза
  порождает несколько сессий по числу subtask'ов этой фазы, не одну).
- `PipelineActorHandlers.cs` — фаза `research` создаёт subtask'и через существующий
  `CreateSubtaskHandler`, вызываемый Planner-сессией на фазе `understand` **до** того,
  как она переходит к созданию `do`-подзадач. Порядок: Planner оценивает зоны
  (Шаг 5), создаёт research-subtask'и, ждёт их завершения, затем создаёт `do`-subtask'и
  уже с учётом находок.

**Подшаги.**
1. Новая фаза в seed-данных `TaskKindHandlers.cs` + маппинг роли в `ISessionSpawner.cs`.
2. Тест: создание задачи дефолтным kind'ом даёт 4 фазы в правильном порядке.

**Acceptance.** Существующие задачи, созданные до этого изменения, не ломаются (миграция
только добавляет новую фазу в seed для новых задач, не трогает `TaskPhase`-записи уже
существующих `TaskItem`).

## Шаг 2 — структурированные находки вместо прозы

**Проблема.** `Summary` — свободный текст; следующий агент либо слепо доверяет ему,
либо вынужден перечитывать файлы заново, чтобы проверить. Нет способа узнать,
что находка устарела.

**Зависит от:** `CodeIndex.HashRange` (`ProjectBeacon-tz-code-semantics.md`, Шаг 3).

**Не трогать:** `Subtask.Summary`, `AllowedMcpToolsJson`/`AllowedPathsJson` — новое поле
по тому же паттерну, не замена существующих.

**Меняем.**
- В `Subtask` (`ProjectBeacon.Domain/Entities/Projects/Subtask.cs`) — новое
  JSON-backed поле `FindingsJson`, тот же паттерн, что `AllowedMcpToolsJson`:
  ```
  public IReadOnlyList<Finding> Findings { get; } // десериализация из FindingsJson
  ```
  `Finding(string Note, string Path, int StartLine, int EndLine, string ContentHash)`.
  `ContentHash` — результат `CodeIndex.HashRange` на момент записи находки.
- Новый MCP-тул `subtask_report_finding` (рядом с уже существующим `subtask_report_result`
  в `McpStdioServer.cs`) — добавляет одну находку к `research`-subtask'у, не заменяет
  весь список разом; вызывается многократно за сессию.
- Миграция — только новый столбец, additive.

**Подшаги.**
1. Поле + сериализация в `Subtask.cs`, миграция.
2. Хендлер `ReportFindingHandler` + команда, по образцу существующего
   `subtask_report_result`.
3. Тул `subtask_report_finding` в `McpStdioServer.cs`.
4. Тест: находка с несуществующим диапазоном (файл короче `EndLine`) — явная ошибка
   при записи, не тихо усечённая находка.

**Acceptance.** Research-subtask может накопить несколько находок за время своей
сессии; каждая хранит `ContentHash` на момент записи.

## Шаг 3 — передача находок в `do`/`understand`, с проверкой устаревания

**Проблема.** Даже с находками в БД их никто не читает при построении промпта
следующей фазы.

**Зависит от:** Шаг 2 этого документа; `CodeIndex.HashRange` для перепроверки.

**Не трогать:** `SessionPrompts.Review` — не меняется, по-прежнему собирает `Summary`.
Изоляция actor-от-actor внутри `do` — не снимается, только добавляется отдельный,
явно поименованный источник (`research`-находки).

**Меняем.**
- `SessionPrompts.cs` — новый приватный помощник `AppendResearchFindings`, вызываемый
  из `Planner` (строит план по находкам) и из `Actor` (видит находки, относящиеся к его
  `AllowedPaths`, а не все находки задачи).
- Перед вставкой в промпт — пересчитать `CodeIndex.HashRange` по текущему файлу и
  сравнить с сохранённым `ContentHash`. Несовпадение → находка помечается
  `[STALE, re-verify]` в тексте промпта, а не отбрасывается молча (агент сам решает,
  доверять ли ей ещё, но предупреждён).

**Подшаги.**
1. `AppendResearchFindings` + фильтрация по `AllowedPaths` для Actor.
2. Проверка хеша и пометка `STALE`.
3. Тест: находка с совпадающим хешем попадает в промпт чисто; с несовпадающим —
   с пометкой; находка вне `AllowedPaths` актёра — не попадает вообще.

**Acceptance.** Промпт `do`-подзадачи, созданной после `research`-фазы, содержит
находки по своим путям; изменение файла между `research` и `do` отражается пометкой,
не тихим устареванием.

## Шаг 4 — лимит на динамическое порождение subtask'ов

**Проблема.** `CreateSubtaskHandler` ничем не ограничен по количеству или глубине —
агент с правом вызывать `task_create_subtask` (research-подзадачи это право получат
в рамках этого ТЗ) при неуверенности может плодить соседей без остановки.

**Не трогать:** сам `CreateSubtaskHandler` для вызовов от Planner — лимит общий,
но Planner обычно создаёт разумное число подзадач за раз осознанно; ограничение
нужно прежде всего против рекурсивного саморазмножения research-агентов.

**Меняем.**
- В `CreateSubtaskHandler.HandleAsync` — проверка перед созданием: число уже существующих
  subtask'ов задачи не превышает конфигурируемый потолок (например, 20 по умолчанию,
  значение в `WorkstationSettings`/конфиге, не хардкод).
- Превышение → `Result.Failure` с понятной причиной, не исключение.

**Подшаги.**
1. Проверка в хендлере + конфигурируемый лимит.
2. Тест: создание N+1-й подзадачи при лимите N — явный отказ, не тихое молчание.

**Acceptance.** Задача не может накопить подзадач больше лимита ни через Planner,
ни через динамическое порождение research-агентами.

## Шаг 5 — бюджетирование зоны у Planner

**Проблема.** Planner режет зоны исследования вслепую, по интуиции о структуре кода,
без проверки объёма или полноты.

**Зависит от:** `GetTree` (уже существует), `GetSignatures`/`GetCallers`
(`ProjectBeacon-tz-code-semantics.md`, Шаги 1–2).

**Не трогать:** сам процесс создания `research`-subtask'ов (Шаг 1) — этот шаг меняет
только то, что Planner делает **перед** созданием, не механику создания.

**Меняем.**
- `SessionPrompts.Planner` — дополнить инструкцией: перед тем как резать зону,
  вызвать `get_tree` для оценки объёма кандидатных файлов и, для символов на границе
  предполагаемой зоны, `get_callers` с проверкой «все прямые вызывающие внутри
  предложенных файлов?». Если нет — либо расширить зону, либо создать для внешнего
  вызывающего отдельный `research`-subtask с пометкой связи.
- Конкретный числовой бюджет (сколько байт/файлов на одного исследователя) —
  не фиксировать в коде заранее; вывести эмпирически через Шаг 6.

**Подшаги.**
1. Текст инструкции в `SessionPrompts.Planner`.
2. Ничего не кодируется как жёсткая проверка на этом шаге — это промпт-инструкция,
   не валидация; Planner остаётся моделью, которая может ошибиться, лимит на число
   subtask'ов (Шаг 4) — единственная жёсткая защита.

**Acceptance.** Ручная проверка на одной реальной задаче: Planner перед созданием
research-subtask'ов реально вызывает `get_tree`/`get_callers`, видно в транскрипте
сессии.

## Шаг 6 — измерение эффекта через eval harness

**Проблема.** Экономия контекста от узких исследователей и структурированных
находок — пока гипотеза, не измеренный факт.

**Зависит от:** существующий `EvalRun`/`EvalCondition` (построен ранее, вне этого ТЗ).

**Не трогать:** существующие условия `WithBrief`/`WithoutBrief`.

**Меняем.**
- Новое значение `EvalCondition.WithResearchPipeline` — прогон задачи через полный
  `research → understand → do → check` путь этого ТЗ, сравнение по токенам/числу
  повторных открытий одного и того же файла против `WithBrief` без research-фазы.

**Подшаги.**
1. Enum-значение (additive) + прогон `EvalPairHandler` с третьим условием.
2. Отчёт `context-cost` (уже существует) расширяется новой колонкой для сравнения,
   не переписывается.

**Acceptance.** На одной и той же задаче есть сравнимые числа для всех трёх условий,
а не только оценка на глаз.

## Порядок

Шаги 1 → 2 → 3 последовательны (каждый зависит от предыдущего). Шаг 4 независим,
можно делать параллельно с 1–3, но до включения research-агентам права на
`task_create_subtask` в проде. Шаг 5 зависит от готовности `ProjectBeacon-tz-code-semantics.md`
(Шаги 1–2) и логически следует после Шага 1. Шаг 6 — последний, подтверждает
или опровергает всю затею на реальных данных.
