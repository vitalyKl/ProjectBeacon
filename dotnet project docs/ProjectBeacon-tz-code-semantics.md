# ТЗ 1 — Семантический слой CodeIndex: сигнатуры и граф вызовов

Формат — как в `ProjectBeacon-fix-plan.md`. Этот документ самодостаточен относительно кода,
но его Шаг 3 (хеш для контроля устаревания) используется вторым ТЗ (`ProjectBeacon-tz-research-pipeline.md`).

## Контекст

`ProjectBeacon.Application/CodeIndex/CodeIndex.cs` сейчас даёт три метода — `GetTree`, `Search`,
`GetChangedScope` — все текстовые/файловые, без единого байта понимания грамматики языка.
Единственное место, где `CodeIndex` создаётся — `ProjectBeacon.Cli/McpStdioServer.cs`: класс целиком
живёт на машине демона и работает с реальными файлами напрямую, серверная сторона его не видит.
Ни Roslyn, ни tree-sitter в проекте сейчас не подключены — это новые зависимости.

Назначение нового слоя: дать research-подзадачам и Planner'у способ понять форму кода
(«что это за символ, кто его вызывает») без чтения файлов целиком и без grep по именам,
который путает одноимённые символы в разных классах.

## Принципы неразрушения

1. `GetTree`/`Search`/`GetChangedScope` не трогаются и не меняют поведение.
2. Новые методы — в том же классе `CodeIndex`, тот же паттерн возврата (`Result<T>`,
   record-типы для результатов), та же регистрация тулов в `McpStdioServer.cs`
   (`Tool("name", "description", ...)`), никакого нового формата ответа.
3. Там, где точный бэкенд (Roslyn) недоступен или решение не собирается — явная,
   видимая агенту деградация («backend: heuristic» / отдельное поле уверенности
   в ответе), а не молчаливый провал и не исключение, уронившее MCP-сессию.
4. Новые NuGet-зависимости (`Microsoft.CodeAnalysis.CSharp.Workspaces` для Roslyn,
   выбранный tree-sitter .NET-биндинг) — только в `ProjectBeacon.Cli` и/или
   `ProjectBeacon.Application`, не в `Domain`.

## Шаг 1 — `GetSignatures(path)`: извлечение сигнатур

**Проблема.** Research-агент сейчас может либо прочитать файл целиком, либо грепнуть текст —
среднего («форма без тела») не существует.

**Не трогать:** `GetTree`, `Search`.

**Меняем.**
- Новый метод `CodeIndex.GetSignatures(IReadOnlyCollection<string> paths) -> Result<SignatureResult>` —
  один вызов, несколько файлов за раз, тот же стиль, что уже есть у `paths` в существующем
  `Search`. Парсинг по-прежнему независим файл от файла (см. ниже про `MSBuildWorkspace`) —
  батч нужен только чтобы не платить за отдельный MCP round-trip на каждый файл зоны.
- `SignatureResult(IReadOnlyList<FileSignatures> Files, string Backend)`,
  `FileSignatures(string Path, IReadOnlyList<SymbolSignature> Symbols, string Backend, string? Error)`,
  `SymbolSignature(string Name, string Kind, string Signature, int Line, string? DocComment)`.
  `Backend` на `FileSignatures` — источник истины, одно из `"roslyn"` / `"heuristic"` /
  `"unsupported"` (язык без экстрактора — явно помечен, не притворяется ни одним из двух
  реальных бэкендов). `Backend` на `SignatureResult` — производное: совпадающее значение,
  если оно одно на весь батч, иначе `"mixed"` — батч файлов разных языков по конструкции
  не может иметь единый бэкенд, и поле на уровне результата должно это показывать, а не
  молчать. `Error` на отдельном `FileSignatures` — файл с синтаксической ошибкой не валит
  весь вызов, остальные файлы в том же батче возвращаются как обычно.
- Интерфейс `ISignatureExtractor` с двумя реализациями:
  - `RoslynSignatureExtractor` — через `Microsoft.CodeAnalysis.CSharp`, парсинг **каждого
    файла по отдельности** (`CSharpSyntaxTree.ParseText` в цикле по `paths`, без
    `MSBuildWorkspace`) — сигнатуры не требуют семантической модели всего решения, только
    синтаксис объявлений, и батч нескольких файлов за вызов этого не меняет: кросс-файловая
    связь между ними всё равно не считается ни в этом варианте, ни в однофайловом.
  - `HeuristicSignatureExtractor` — через tree-sitter, для файлов не на C#, тем же
    по-файлово-независимым циклом. В рамках этого шага реализовать для **одного**
    дополнительного языка, который реально используется в ваших проектах (TypeScript —
    под Haven, либо GDScript — под CoreBrakers, выбрать по тому, с чем работаете чаще);
    остальные языки — явный `NotSupported` на конкретном файле, не попытка угадать по
    эвристике без грамматики.
- Выбор реализации — по расширению файла, без автоопределения по содержимому; один вызов
  может смешивать файлы разных языков, каждый обрабатывается своим бэкендом независимо.

**Подшаги.**
1. `ISignatureExtractor` + `RoslynSignatureExtractor` (цикл по `paths`, каждый файл
   независимо, без Workspace).
2. `HeuristicSignatureExtractor` для одного выбранного языка, тем же циклом.
3. Регистрация тула `get_signatures` в `McpStdioServer.cs`, тот же паттерн, что `get_tree`.
4. Тесты: батч из нескольких `.cs`-файлов за один вызов → по записи `FileSignatures`
   на каждый, `Backend` результата == `"roslyn"`; один файл в батче с синтаксической
   ошибкой → `Error` только у него, остальные файлы батча всё равно возвращают сигнатуры;
   файл неподдерживаемого языка → `Backend: "unsupported"` на этом файле, не падение
   всего вызова; батч из `.cs` + поддерживаемого второго языка → `Backend` результата
   == `"mixed"`, при этом у каждого `FileSignatures` свой корректный бэкенд.

**Acceptance.** Один вызов на несколько реальных `.cs`-файлов из `ProjectBeacon.Domain`
возвращает сигнатуры публичных методов/свойств без тел по каждому файлу; `Backend == "roslyn"`;
результат — один round-trip, не N отдельных вызовов тула на N файлов зоны.

## Шаг 2 — `GetCallers(symbol)`: входящие ссылки, один хоп

**Проблема.** Нужен способ проверить, что предполагаемая зона исследования не упускает
вызывающих снаружи — без рекурсивного обхода графа, у которого нет естественной
точки остановки.

**Не трогать:** `GetSignatures` из Шага 1 — используется как есть для получения координат
символа, не переписывается.

**Меняем.**
- Новый метод `CodeIndex.GetCallers(string path, string symbolName, int line) -> Result<CallerResult>`.
- `CallerResult(string Symbol, IReadOnlyList<CallerSite> Callers, string Backend, bool? SolutionBuilds)`.
- `CallerSite(string Path, int Line, string Snippet, string? Symbol)` — `Symbol` это имя
  окружающего метода/свойства вызывающей стороны (например, `BarService.Process`), не
  просто координата строки. Для Roslyn это уже вычисляется попутно при резолве локации
  ссылки, лишней работы не требует. Для heuristic-бэкенда — подъём по синтаксическому
  дереву от найденной строки до ближайшего объявления функции, тоже не требует разрешения
  типов. `null`, если вызов лежит вне какого-либо именованного символа (top-level код).
  Без этого поля Planner получил бы только `Foo.cs:42` и был бы вынужден открывать файл,
  чтобы понять, кто именно вызывающий.
- **Жёсткое ограничение: один хоп.** Метод возвращает только прямых вызывающих найденного
  символа — не вызывающих вызывающих. Транзитивное расширение — забота Planner'а/агента:
  они решают, идти ли дальше, вызывая метод повторно на новом символе, а не получают
  это автоматически.
- Roslyn-реализация: `MSBuildWorkspace` + `SymbolFinder.FindReferencesAsync` — требует,
  чтобы решение собиралось. Если загрузка/компиляция падает — возвращать `Result.Failure`
  с понятной причиной и `SolutionBuilds: false`, не бросать необработанное исключение
  в MCP-сессию.
- Heuristic-реализация (tree-sitter, тот же язык, что в Шаге 1): текстовый поиск вызовов
  по имени символа без разрешения типов. **Явно настроить на recall, не precision** —
  для этой задачи пропущенный настоящий вызывающий опаснее лишнего совпадения:
  агент тратит немного контекста на нерелевантный файл, но не остаётся с дырой в зоне.

**Подшаги.**
1. `ICallerFinder` с Roslyn- и heuristic-реализациями, по аналогии со Шагом 1.
2. Деградация при несобирающемся решении — отдельный тест: веткой с синтаксической
   ошибкой в одном файле, `GetCallers` на символ из другого файла того же решения
   не должен падать с необработанным исключением.
3. Регистрация тула `get_callers` в `McpStdioServer.cs`.
4. Тест на реальный случай «один хоп, не дальше»: символ с известными вызывающими
   второго уровня — ответ не должен включать их.

**Acceptance.** На символе с несколькими известными прямыми вызывающими в разных файлах
решения — `GetCallers` находит всех, не включает вызывающих вызывающих.

## Шаг 3 — хеш диапазона для контроля устаревания

**Проблема.** Находки, записанные research-подзадачей (см. `ProjectBeacon-tz-research-pipeline.md`,
Шаг 2), должны уметь объявлять себя устаревшими, если код с тех пор изменился. Персистентной
таблицы индексированных файлов с хешами в проекте нет — `CodeIndex` работает вживую по
каждому вызову, ничего не хранит между вызовами.

**Не трогать:** Шаги 1–2 этого документа.

**Меняем.**
- Новый метод `CodeIndex.HashRange(string path, int startLine, int endLine) -> Result<string>` —
  детерминированный хеш (например, SHA-256) содержимого указанного диапазона строк файла
  на момент вызова. Не привязан к git — работает и для незакоммиченных изменений.
- Это чистая, дешёвая функция без парсинга — читает диапазон строк и хеширует текст.
  Используется и при записи находки (Шаг 2 второго ТЗ), и при её последующем чтении,
  чтобы сравнить «тогда» и «сейчас».

**Подшаги.**
1. Метод + тесты (одинаковый диапазон → одинаковый хеш; изменённая строка внутри
   диапазона → другой хеш; изменение вне диапазона → хеш не меняется).
2. Регистрация тула `hash_range` в `McpStdioServer.cs` — используется в основном
   программно вторым ТЗ, но полезен и агенту напрямую, если он хочет сам проверить
   актуальность цитаты.

**Acceptance.** Независимая проверка: изменить строку внутри диапазона → хеш другой;
изменить соседнюю строку вне диапазона → хеш тот же.
