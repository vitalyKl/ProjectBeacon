# ProjectBeacon — сводный анализ

Репозиторий: `github.com/vitalyKl/ProjectBeacon` (.NET 9, Blazor Server + MudBlazor, EF Core/Postgres).
Метод: статическое чтение кода (сборка/тесты не запускались — нет .NET SDK и доступа к NuGet в песочнице),
контраст цветов посчитан по формуле WCAG из реальных hex-значений темы, все находки по документации —
прямое построчное сопоставление с кодом.

Каждый пункт — конкретная находка с указанием файла, а не общее впечатление.

---

## 0. Как читать этот документ

- 🔴 — потенциально серьёзно (безопасность, потеря данных, недоступность функции для части пользователей)
- 🟡 — реальная проблема среднего масштаба (архитектурный риск, несогласованность, устаревшая документация)
- ⚪ — мелкая находка / стилистическая непоследовательность

## 1. Backend / архитектура (Application, Infrastructure, API)

### 🟢 Сильные стороны (для контекста)
- Tenant isolation спроектирована правильно: `AsyncLocal`-скоуп с `IDisposable`-восстановлением, fail-closed
  (`null` ProjectId никогда не означает «без скоупа», только явный `EnterUnscoped()`).
- Единственный сырой SQL во всём проекте (`ClaimTaskHandler`, `FOR UPDATE SKIP LOCKED`) параметризован,
  инъекций нет.
- Аутентификация: BCrypt только в Infrastructure, токены хранятся как хэш и показываются один раз,
  rate limiting на auth-эндпоинтах, forgot-password всегда 200 (без user enumeration).

### 🟡 `ClaimTaskHandler` — неявная зависимость от tenant-фильтра
Сырой SQL фильтрует только по `Id` и `Status = 'Todo'`, без `ProjectId` в запросе. Безопасность полностью
делегирована тому, что EF Core сам подставит global query filter поверх `FromSqlRaw` как подзапрос — это
подтверждается тем, что единственный тест на этот путь (`ClaimTaskPostgresTests`) оборачивает вызовы в
`TenantScope.EnterUnscoped()`, иначе claim не проходит вообще. При этом нет теста, доказывающего, что участник
проекта A не может забрать чужую задачу проекта B через маршрут `/v1/tasks/{taskId}/claim` (без `projectId` в
пути) — есть только тесты на конкурентность (оба запускаются unscoped).
**Рекомендация:** явный `WHERE "ProjectId" = {1}` в самом SQL + тест `NonMember_CannotClaimForeignProjectTask`.

### 🟡 `TenantIsolationMiddleware.InvokeAsync` — избыточная плотность логики
~90 строк вложенных условий, разрешающих project/org-скоуп из route/header/claim/membership/admin-fallback.
Логика прослеживается и корректна (fail-closed), но такая плотность в самом security-критичном месте — риск
для будущего аудита и рефакторинга. Стоит разбить на именованные, независимо тестируемые шаги.

### ⚪ `GenerateRandomPassword` — modulo bias
`bytes[i] % chars.Length` по 70-символьному алфавиту из `RandomNumberGenerator.GetBytes` — классическое
смещение (256 не делится на 70 нацело). Не критично для 32-символьного пароля, но `RandomNumberGenerator.GetInt32`
устраняет это бесплатно.

### ⚪ Нет глобального exception-handling middleware
`Program.cs` не регистрирует `UseExceptionHandler`/`ProblemDetails`. Утечки стектрейса в Production нет
(дефолт ASP.NET Core), но нет и единого формата ответа/логирования для необработанных исключений.

### ⚪ `Result<bool>` как замена `void`
~40 обработчиков команд используют `Result<bool>` там, где нет возвращаемого значения. Небольшая
непоследовательность именования, не более.

## 2. Локальный демон (`beacon client`, `ProjectBeacon.Cli/Client`)

### 🔴 Токен устройства (`bcd_...`) хранится в чистом виде без защиты ОС
`ClientStore` пишет токен в `%LOCALAPPDATA%\ProjectBeacon\client.json` (или XDG-эквивалент) обычным JSON.
Ни `SetUnixFileMode`/ACL, ни DPAPI/Keychain — не используются нигде в проекте (проверено grep'ом). Это
единственное расхождение с тем, как аккуратно токены хранятся на сервере (только хэш, показ один раз) —
и это самый ценный локальный секрет: демон владеет рабочим деревом и умеет выполнять команды.

### 🔴 Отсутствие sandbox для файловых операций, управляемых сервером
`WorkstationActions.ListDir / InitProject / ApplyOpencode / ScanGguf` берут `path` прямо из payload команды
(пришедшей от control plane по long-poll) и только делают `Path.GetFullPath(path)` — без allowlist-корня,
без проверки принадлежности `ProjectsRoot`/`ProjectRuntime.LocalRoot`. Для сравнения: локальный MCP-сервер
(`FileWorkspace` + `WorkspacePath.ResolveInsideRoot`) — то же самое действие, но с настоящей песочницей
(есть unit-тесты на отказ `../`). У аналогичного, но server-driven пути такой защиты нет вообще.
Последствие: при компрометации/краже `bcd_`-токена (см. пункт выше) атакующий получает перечисление
всей файловой системы (`ListDir`) и создание директорий/git init/запись конфигов в любом доступном для
записи месте — не только в папке проектов.
**Рекомендация:** тот же `ResolveInsideRoot`-паттерн, что уже есть в `FileWorkspace`, применить к
`WorkstationActions`, ограничив корнем конкретного `ProjectRuntime`.

### 🟡 `ChatPromptAsync` — хрупкая эвристика завершения генерации
Поллинг новых частей ответа каждые 250мс, «конец» определяется как 6 подряд пустых опросов (**1.5 секунды
тишины**) либо жёсткий потолок в 240 итераций (**60 секунд**), после чего безусловно шлётся `/idle`. Для
локальных моделей (особенно CPU-инференс — ровно то, для чего проект и задуман) 1.5с паузы между токенами —
обычное дело, не аномалия. Долгая генерация дольше 60с молча обрывается без ошибки — пользователь просто
видит «待/idle», а не факт обрыва.

### ⚪ `ErrorDelay` — вводящее в заблуждение имя
Поле называется `ErrorDelay`, но фактически используется как **обычный** интервал heartbeat (применяется
после каждой успешной итерации). Настоящий error-backoff использует захардкоженный `TimeSpan.FromSeconds(3)`
вместо отдельного именованного поля (как `CommandErrorDelay` для команд).

### ⚪ Синхронный `Dispose()` поверх async
`_openCode.DisposeAsync().AsTask().GetAwaiter().GetResult()` — блокирующий anti-pattern. Низкий риск в
консольном приложении без sync context, но incident-prone паттерн, если код когда-то переиспользуют.

### Не баг, но важная граница доверия
`LocalModelBackend.LaunchCommand` (настраивается через Web UI любым участником проекта с правами на модели)
попадает в YAML, который затем **внешний** бинарник `llama-swap` исполняет на машине разработчика. Сам демон
эту строку не шеллит напрямую — но право редактировать конфиг модели де-факто равно праву исполнить
произвольную команду на чужой рабочей станции.

## 3. Web UI — качество кода

### 🟢 Сильные стороны
- `BeaconDbContext` ни разу не инжектится в `.razor` (проверено grep'ом по всем компонентам) — свой же
  запрет из `AGENTS.md` реально соблюдается.
- Нет `MarkupString`/`@Html.Raw` нигде — закрыт главный XSS-вектор Blazor.
- Нет JS interop вообще (`IJSRuntime` не используется) — соответствует правилу «No custom JS».
- `ErrorBoundary` корректно `@key`'нут на `Navigation.Uri` — без этого он бы не сбрасывался при навигации
  (частая ошибка Blazor).
- Open-redirect защита в `/v1/auth/cookie-login` закрывает и `//...`, и `\`-обход — многие делают только
  первую проверку.
- Локализация реально соблюдена: скан всех `.razor` на захардкоженный английский текст вне `@`-выражений
  дал ноль совпадений.

### 🟡 «Edge Playwright ✅» в роадмапе ничем не подкреплены в репозитории
В `dotnet project docs/ProjectBeacon-dotnet-roadmap-v2.md` многократно фигурируют формулировки вида
«Edge Playwright: drag `.mud-drop-item` Todo→InProgress...», «Reports generate/list snapshot», «Decisions
create+accept». Проверено: **в решении нет ни Playwright, ни bUnit** ни в одном csproj. `ProjectBeacon.Web.Tests`
(9 файлов) тестирует только то, что вынесено из UI-слоя (полнота локализации, rate-limit конфиг, cookie-login
редиректы, tenant-isolation middleware, расчёт token-budget meter, палитра чипов) — ни одного рендеринга
компонента или симуляции клика/drag. CI (`ci.yml`) запускает только `dotnet test`, который эти сценарии
никогда не затрагивает. Значит каждая такая ✅-отметка — разовая ручная/агентская проверка, а не
регресс-тест: drag-and-drop, диалоги, Settings — ничего из этого не защищено от тихой поломки при рефакторинге.

### 🟡 Cookie `SecurePolicy = SameAsRequest` без `UseForwardedHeaders`
`HttpOnly = true`, `SameSite = Strict` заданы хорошо. Но `SecurePolicy = CookieSecurePolicy.SameAsRequest` при
полном отсутствии `UseForwardedHeaders`/`ForwardedHeadersOptions` в коде — а именно это нужно именно для
задокументированного production-пути (`deploy/README.md`, K8s blue-green с TLS-termination на ingress).
Если под, получающий трафик, видит его как plain HTTP (типичная схема), `Request.IsHttps` будет `false`,
и auth-cookie молча выпустится **без флага `Secure`**, несмотря на то что клиент видит HTTPS end-to-end.

### 🟡 «God-компоненты»
`Settings.razor` — 710 строк, **20 отдельных `@inject`**-хэндлеров (участники, инвайты, смена пароля, лейблы,
устройства, команды, runtime — 6-7 не связанных зон ответственности в одном файле). `TaskDetail.razor` — 670
строк, ~45 членов в `@code`. Ничего не сломано функционально, но обе страницы давно превысили порог, за
которым компонент тестируем/ревьюируем как единица.

### ⚪ `Board.razor` — непоследовательный показ ошибок
Провал загрузки списка задач выставляет `_error = true` и показывает состояние ошибки; провал загрузки
labels/milestones в том же методе молча деградирует до пустого списка без индикации. «Успешна ли страница» —
не единый надёжный сигнал.

## 4. UX / доступность (по разметке и стилям)

### 🔴 Контраст цвета — посчитан по формуле WCAG, не на глаз
| Пара | Коэффициент | AA (4.5:1 для обычного текста) |
|---|---|---|
| `WarningContrastText` на `Warning` (light) | **2.85:1** | ❌ Провал |
| `SuccessContrastText` на `Success` (light) | **3.58:1** | ❌ Провал (проходит порог 3:1 для крупного текста/UI) |
| `PrimaryContrastText` на `Primary` (dark) | **3.52:1** | ❌ Провал (проходит порог 3:1) |
| `TextSecondary` на `Background` (light) | 4.40:1 | На грани провала |

Любой заполненный `Warning`-чип/кнопка/алерт рендерит тёмно-коричневый текст на янтаре при <3:1 — реально
трудно читать, не пограничный случай. Правка — в одной строке `BeaconTheme.cs`.

### 🔴 У Kanban-доски нет способа переместить задачу без drag-and-drop
Единственный способ сменить статус задачи — `MudDropContainer`/`OnItemDropped` в `Board.razor`. Проверено:
на `TaskDetail.razor` статус показан только как read-only `MudChip` (нет `MudSelect`/кнопок), на
`Backlog.razor` — то же самое, никакого альтернативного контрола нигде нет. Пользователь с клавиатуры,
скринридером или без надёжного drag на тачскрине **физически не может провести задачу через жизненный цикл**
через UI — это центральный сценарий трекера задач с одним-единственным способом взаимодействия.
**Рекомендация:** `MudSelect` статуса на `TaskDetail.razor`, дергающий тот же `ChangeTaskStatusHandler`.

### 🟡 Нет responsive-вёрстки для самого приложения
Во всём `app.css` — ровно один `@media`-запрос, и тот только для `.landing-mock`/`.landing-mock-cols`
(маркетинговая лендинг-страница). У самого приложения нет ни одного брейкпоинта:
- `DrawerWidthLeft: 168px` фиксирован без правила схлопывания.
- `.beacon-chat-dock { width: 360px; position: fixed; right: 24px; bottom: 24px }` без фолбэка — на экране
  ~375-414px либо вылезает за край, либо не оставляет отступов.
- Kanban-доска деградирует в горизонтальный скролл — это не осознанное решение дизайна (нет media query,
  которая бы это выбирала), а просто поведение flex/overflow по умолчанию.

### ⚪ Обе icon-only кнопки в приложении без доступного имени
Во всём приложении ровно два `MudIconButton` (удаление задачи в `Backlog.razor`, закрытие чата в
`ChatDock.razor`) — ни у одного нет `Title`. Дешёвая правка; остальная навигация всегда сопровождает иконку
текстом.

### ⚪ Нет `MudTooltip` и явных `aria-*` атрибутов нигде
Полагается целиком на встроенный ARIA MudBlazor. Особенно ощутимо для нестандартных виджетов — drag-and-drop
доски и token-budget meter.

### ⚪ Фокус-индикация едва заметна
`.beacon-card-interactive` показывает фокус только сдвигом цвета рамки + крошечной точкой 8×8px
(`.beacon-status-dot`), без outline/box-shadow. В сочетании с отсутствием клавиатурного способа сменить
статус (см. выше) — клавиатурная навигация по доске одновременно плохо видна и никуда не ведёт.

## 5. Размеры и отступы

### 🟡 Три параллельные системы отступов вместо одной
В `app.css` в `:root` объявлена полноценная шкала `--space-1`…`--space-16` (4px…64px) — и **используется
0 раз** в том же файле; каждый `padding`/`margin` написан заново как сырое число. Отдельно существует
спейсинг-система MudBlazor-утилит (`pa-4`, `mt-2`…), которая реально применяется в разметке, и её числа
случайно совпадают со шкалой из CSS — но это два независимых источника истины для одних и тех же величин.
Часть сырых чисел в CSS выбивается даже из собственной 4px-сетки: `padding: 7px 8px` (nav-link),
`padding: 10px` (карточка доски), `padding: 2px 8px` (маленький чип), `padding: 1rem 1rem 1rem 3.7rem`
(error boundary).

### ⚪ Дублирование ширины drawer
`BeaconTheme.cs`: `LayoutProperties.DrawerWidthLeft = "168px"`, и тут же `MainLayout.razor` повторно
хардкодит `<MudDrawer Width="168px">`. Явный `Width=` перекрывает тему — тема-значение сейчас мёртвое именно
из-за этого дубля.

### 🟡 Непоследовательное ограничение ширины контента
Во всём приложении нет ни одного `MudContainer`. Единственное ограничение — `<div class="pa-8">` вокруг
`@Body` в `MainLayout.razor`, чистый паддинг без `max-width`. Класс `.beacon-form { max-width: 520px }`
в CSS существует, но применён **ровно в одном месте** (`New.razor`, создание проекта) — на `Settings.razor`
(форма из 20+ полей) не применён вовсе. До логина (`.auth-card`, 400px) ширина ограничена честно и
последовательно — после логина паттерн «формы должны иметь max-width» соблюдён почти нигде.

### 🟢 Что сделано последовательно
- Все диалоги во всём приложении используют один и тот же `DialogOptions { MaxWidth.Medium, FullWidth = true }`.
- `Size="Size.Small"` — единственное встречающееся значение `Size=` во всём приложении (80 раз), без микса
  с `Medium`/`Large`.
- Нет ни одного inline `style="..."` ни в одном `.razor`-файле — вся стилизация идёт через классы/пропсы.

## 6. Документация vs реальность

Здесь речь не о качестве текста, а о конкретных построчных расхождениях между тем, что написано в
`AGENTS.md`/`README.md`/roadmap, и тем, что реально в коде/репозитории.

### 🔴 `AGENTS.md`: описание worker-токена не соответствует коду
Раздел Security: *«The worker actor (`BEACON_WORKER_TOKEN`) is a root credential: `actor.kind === "worker"`
is treated as project admin on every project.»* Это JS/TS-синтаксис (`===`, `actor.kind`) — калька со старой
TypeScript-реализации. Реальный C#-код (`FinishWorkCommand.cs`, `PipelineHandlers.cs`) не имеет никакого
`actor.kind` вообще: он напрямую сравнивает bearer-токен с `BEACON_WORKER_TOKEN` через
`FixedTimeEquals(actorId, workerToken)`. Это самая security-значимая строка документа (предупреждает не
печатать root-credential) — и она описывает механизм, которого в коде не существует. Тот, кто будет
аудировать код по этой строке, будет искать несуществующее поле `actor.kind`.

### 🟡 `apps/mcp` и `packages/ui` — пути из старого TS-монорепо, которых нет в дереве
`AGENTS.md`, раздел Non-goals: *«`apps/mcp` HTTP is control-plane only»* и *«`packages/ui` stays a stub»*.
В текущем .NET-репозитории **нет ни `apps/`, ни `packages/`** на любом уровне (проверено `find`). Это
буквальные пути из удалённой TypeScript-структуры, перенесённые в документ без адаптации к реальным именам
проектов (`ProjectBeacon.API` и т.п.).

### 🟡 `typescript/` — заявлен как справочная копия, но не существует в клонированном репозитории
`AGENTS.md`, Architecture: *«.NET 9 monorepo (C#). Rebuild of the TypeScript implementation (now in
`typescript/`).»* В `.gitignore` эта папка явно исключена (`typescript/ # legacy`), а история git подтверждает
коммит *«chore: remove root TypeScript tree from git ... A copy remains under gitignored typescript/ for
reference»*. То есть папка существовала только локально у автора на момент того коммита — при свежем клоне
(как в этом анализе) её просто нет. Документ описывает состояние машины автора, а не состояние репозитория.

### 🟡 Список пунктов drawer в README.md и AGENTS.md устарел — не хватает «Chat»
Оба документа перечисляют: *«Dashboard, Board, Backlog, Roadmap, Context, Decisions, Agents, Reports,
Settings»* (README — в разделе Self-host, AGENTS.md — в Pitfalls). Реальный `MainLayout.razor` содержит **10**
пунктов, включая `/chat` (иконка `Icons.Material.Filled.Chat`) — этого пункта нет ни в одном из двух
перечислений. Судя по миграции `AddChatSessions` (2026-09-20) и `Chat.razor`/`ChatDock.razor`, фича Chat
добавлена позже, чем были написаны эти строки, и оба места забыли обновить.

### ⚪ Тестовые числа в roadmap M6 уже устарели
Roadmap: *«dotnet test green (Domain 117, Application 120, Infrastructure 26, API 32, Web 44)»*. Текущий
подсчёт `[Fact]/[Theory]` по проектам: Domain **128**, Application **153**, Infrastructure **28**, API **38**,
Web **40**. Рост в целом ожидаем (разработка продолжилась после этой строки), но у Web счётчик **упал**
(44→40) — стоит перепроверить, не были ли какие-то тесты удалены/объединены без следа в документе.

### ⚪ `.env.example` предзаполняет `JWT__Secret`, хотя README подразумевает, что его нужно «установить»
README, Self-host: *«Copy `.env.example` to `.env` and set `POSTGRES_PASSWORD` and/or
`ConnectionStrings__Default`, `BOOTSTRAP_ADMIN_TOKEN`, and `JWT__Secret`.»* Но в самом `.env.example`
`POSTGRES_PASSWORD`, `BOOTSTRAP_ADMIN_TOKEN` и `BEACON_WORKER_TOKEN` оставлены пустыми (наглядно требуют
заполнения), а `JWT__Secret` уже содержит готовое на вид значение
(`ProjectBeacon-JWT-Secret-Key-Must-Be-At-Least-32-Characters-Long`). Самовольный self-host, следующий
инструкции README буквально, может просто скопировать `.env.example` в `.env` и не заметить, что
`JWT__Secret` нужно поменять — в отличие от явно пустых полей, ничто в разметке файла не сигнализирует, что
это значение обязательно к замене.
