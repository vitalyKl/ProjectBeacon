# ProjectBeacon — решения по открытому контракту предложений

Дата: 10 ноября 2026  
Основа: `ProjectBeacon-proposals-and-markdown-plan.md`, раздел 8.  
Статус: решения для реализации; контракт уточнён до начала P2.

## Принятые решения

| Вопрос | Решение | Основание и следствие |
|---|---|---|
| Описание проекта как отдельная цель | **Да, отдельный `ProjectDescription`.** | Описание проекта — самостоятельное принятое содержимое с собственной ревизией. Секции Context не должны становиться его суррогатом. TargetId совпадает с ProjectId. |
| Закрытие пайплайна при ожидающих предложениях | **Не блокировать; предупреждать.** | Ожидающее предложение само по себе не должно удерживать задачу и мешать завершению. При закрытии и пробуждении планера показываются счётчики Pending/Conflicted; политика блокировки может быть добавлена отдельно, но не включается сейчас. Истёкшие, отклонённые и отозванные предложения не считаются ожидающими. |
| Кто принимает предложения к Decision и Constraint | **Только Owner/Admin проекта или Owner/Admin организации проекта.** | Принятие решения или правила — действие управления проектом. Member может создавать и просматривать предложения в рамках доступа проекта, но не может утвердить/отклонить governance-изменение. Для прочих целей применяется обычное человеческое право записи по проекту; системные администраторы сохраняют доступ по существующей модели. |
| Можно ли отключить Expired | **Нет в первой версии. TTL фиксирован — 30 дней.** | Бессрочные Pending создают неограниченный операционный долг. Истёкшая запись сохраняется в истории и аудите; продление/повторная подача — отдельное новое предложение. Никакая очистка истории не выполняется. |
| RepoPatch: код и документация | **Review допускается только для документационных профилей и разрешённых путей docs/README. Для кода общий Review не включать.** | Другие акторы не увидят непринятый патч, поэтому согласование кода через общую очередь создаёт ложную картину рабочего дерева. Код остаётся в текущем изолированном цикле правок и проверки. Автоприменение документации остаётся явной настройкой профиля, не глобальным поведением. |

### Уточнение границы проектного доступа для P2

Для строки «обычное человеческое право записи по проекту» используется существующая модель членства: любой участник проекта с ролью Owner, Admin или Member может создавать, просматривать и принимать/отклонять предложения по обычным целям. Owner/Admin проекта, Owner/Admin организации проекта и системный администратор также имеют доступ. Членство в организации с ролью Member без членства в конкретном проекте не даёт доступа к Inbox этого проекта. API-токен не считается человеком: он может только подать или отозвать собственное предложение при наличии ContextRead и валидной привязки к активной Actor-сессии.

## Обязательные инварианты реализации

1. Агент не принимает, не отклоняет и не редактирует статус чужого предложения. Эти операции доступны только человеку; для Decision/Constraint — только Owner/Admin.
2. Новое предложение привязано к проекту, задаче, подзадаче и активному Actor pipeline session. Идентификаторы автора, роли и профиля получаются на сервере, а не принимаются из payload.
3. При принятии проверяется `BaseRevision`. Несовпадение сохраняет статус `Conflicted`, не меняя целевое содержимое и не создавая ContentVersion.
4. Применение целевого изменения, новая ContentVersion, новый статус предложения и событие аудита сохраняются атомарно.
5. Откат принятого предложения создаёт новую ревизию через существующий ContentWriter; история не переписывается.
6. Повторный запрос принятия уже принятого предложения идемпотентен и возвращает сохранённый результат.
7. Содержимое предложения — недоверенные данные. Аудит содержит только allowlisted метаданные, но не Markdown, diff, payload, rationale, токены или пути с секретами.

## Границы фаз

- **P2:** модель и жизненный цикл Proposal, права, атомарное принятие/отклонение/отзыв/конфликт/истечение, аудит и API.
- **P3:** инструменты агента, их роль-профильный allowlist, пробуждение планера.
- **P4:** Inbox, diff/Markdown preview, пакетные операции и история в UI.
- **P5:** политика автопринятия по паре TargetKind × Operation. До завершения P5 всё кроме уже существующего безопасного создания ContextSection остаётся Manual.
- **P6:** RepoPatch. Не расширять его на код до отдельного решения об изолированном состоянии, видимом всем следующим акторам.

Эти решения не меняют уже согласованный контракт Markdown и не оборачивают повторно существующие Proposed Decision/Constraint или NeedsReview ContextSection: они уже являются reviewable drafts.

## Проверенный объём реализации и оставшиеся границы контракта

Проверка кода и тестов 11 ноября 2026 подтверждает следующий поддерживаемый контракт:

- **Update** — существующие revisioned targets: ProjectDescription, ContextSection, Decision, Constraint, Milestone, TaskDescription и документационный RepoPatch. RepoPatch остаётся доступен только `docs-writer` и применяет отдельную строгую политику путей/хешей.
- Для `ContextSection.Update` доступны полный `title/bodyMarkdown` payload и AST-адресуемые `edits[]`: `replace` сохраняет заголовок и меняет тело до следующего заголовка того же или более высокого уровня; `insert_after` добавляет содержимое после всей секции; `delete` удаляет секцию вместе с вложенными подразделами. Заголовок задаётся с уровнем (`## Security`), должен быть уникальным; содержимое внутри fenced code не адресуется. Отсутствующий или неоднозначный заголовок возвращает ошибку с доступным списком, без частичного применения.
- **Create** — новая Milestone. Внешний запрос использует `TargetId = Guid.Empty` и `BaseRevision = 0`; сервер резервирует новый ID до сохранения предложения, поэтому повтор по idempotency key возвращает ту же запись. При принятии Milestone, начальная ContentVersion, состояние Proposal и audit записываются атомарно.
- **Delete** — ContextSection, Milestone, Decision и Constraint. ContextSection/Milestone физически удаляются после записи tombstone ContentVersion; Decision переводится в Deprecated, Constraint — в Rejected. Все четыре перехода требуют текущую ревизию и человеческое подтверждение.
- Существующие создания Decision/Constraint через Proposed и ContextSection через NeedsReview остаются в прежних review-потоках. Они не дублируются вторым Proposal.
- Restore ContextSection/Milestone воссоздаёт прежний target ID только если последняя ContentVersion — ожидаемая deletion tombstone; результат получает новую ревизию. Restore Decision/Constraint восстанавливает статус и содержимое из исторического snapshot как новую ревизию. История не перезаписывается.
- Ручные переходы Accept/Deprecate/Supersede Decision и Activate/Reject Constraint также пишут ContentVersion при изменении статуса; повтор идемпотентного перехода не создаёт фиктивную ревизию.
- Auto по-прежнему разрешён только для RepoPatch Update и только при одновременном разрешении проекта и профиля docs-writer. Create/Delete всегда Manual.

Неподдерживаемые пары остаются отклонёнными: Create для остальных targets, Delete для ProjectDescription/TaskDescription/RepoPatch, а также любая запись кода через RepoPatch. Не превращать их в побочный эффект или обход review-политики. Для создания Decision/Constraint/ContextSection следует использовать указанные legacy review-пути.

**Definition of Done:** P1/P2 проверяются вместе с Create/Delete и восстановлением tombstone; зелёный CI сам по себе не закрывает фазу, пока не подтверждены UI/history entry points, MCP contract, security/RLS и полная матрица тестов на актуальном HEAD.

### Уточнение идентичности Markdown-импорта

- Для импортированного файла ключом повторного импорта является ProjectId + SourcePath в проектном scope. Совпадающий basename из разных каталогов создаёт разные ContextSection; импорт не обновляет Native-раздел Beacon только из-за совпадения SectionId.
- SourcePath — идентификатор и происхождение входного файла; Path остаётся отдельным полем области действия ContextSection и не подменяется им.
- Специализированные файлы сохраняют свои ContextSource; прочие Markdown-файлы получают ImportedMarkdown (Native зарезервирован для содержимого, созданного непосредственно в Beacon).
- При первом повторном импорте старой записи с SourcePath == FileName запись обновляется на месте, а переход к полному SourcePath фиксируется новой ContentVersion. Неоднозначное legacy-сопоставление возвращает Conflict.
- Уникальный частичный индекс защищает импортированный project-scope identity от гонки двух первых импортов. Повторная вставка получает Conflict; частично применённая пачка откатывается.
- Если старую запись с одним basename пытаются сопоставить сразу с несколькими новыми файлами того же имени, импорт останавливается с Conflict вместо произвольного выбора каталога. В CompileBrief импортированные файлы с разными SourcePath включаются отдельно; при совпадении логического SectionId Native-содержимое Beacon имеет приоритет.

### Уточнение квот активных предложений (12 ноября 2026)

- Лимит — **200 активных Pending на проект** и **50 активных Pending на задачу**. Активность определяется одновременно `Status = Pending` и `ExpiresAt > now`; истёкшая запись не занимает квоту, даже если её статус ещё не материализован в `Expired` из-за ограниченной пакетной обработки просроченных строк.
- `Conflicted`, `Applying`, `Accepted`, `Rejected`, `Superseded`, `Withdrawn` и `Expired` не расходуют Pending-квоту. Конфликтное предложение сохраняется и отображается отдельно, но само по себе не удерживает слот.
- Новое предложение того же Actor по той же цели сначала переводит прежнее Pending в `Superseded`, и только после этого рассчитывается доступная квота. Замена не должна блокироваться заполненным лимитом.
- Проверка квот выполняется внутри транзакции **PostgreSQL Serializable**. Это закрывает гонку, при которой два одновременных запроса видели один свободный слот и оба проходили проверку. При повторе execution strategy объект Proposal создаётся заново, чтобы не переносить изменённое доменное состояние из откатившейся попытки.
- Аудит и история истёкших/замещённых/конфликтных предложений не очищаются автоматически; материализация Expired остаётся пакетной и ограниченной.
