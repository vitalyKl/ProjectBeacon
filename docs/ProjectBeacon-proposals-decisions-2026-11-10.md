# ProjectBeacon — решения по открытому контракту предложений

Дата: 10 ноября 2026  
Основа: `ProjectBeacon-proposals-and-markdown-plan.md`, раздел 8.  
Статус: решения для реализации; контракт уточнён до начала P2.

## Принятые решения

| Вопрос | Решение | Основание и следствие |
|---|---|---|
| Описание проекта как отдельная цель | **Да, отдельный `ProjectDescription`.** | Описание проекта — самостоятельное принятое содержимое с собственной ревизией. Секции Context не должны становиться его суррогатом. TargetId совпадает с ProjectId. |
| Закрытие пайплайна при ожидающих предложениях | **Не блокировать; предупреждать.** | Ожидающее предложение само по себе не должно удерживать задачу и мешать завершению. При закрытии и пробуждении планера показываются счётчики Pending/Conflicted; политика блокировки может быть добавлена отдельно, но не включается сейчас. Истёкшие, отклонённые и отозванные предложения не считаются ожидающими. |
| Кто принимает предложения к Decision и Constraint | **Только Owner/Admin проекта или Owner/Admin организации проекта.** | Принятие решения или правила — действие управления проектом. Member может создавать и просматривать предложения в рамках доступа проекта, но не может утвердить/отклонить governance-изменение. Для прочих целей применяется обычное человеческое право записи по проекту; системные администраторы сохраняют доступ по существующей модели. |
| Можно ли отключить Expired | **Нет в первой версии. TTL фиксирован — 30 дней.** | Бессрочные Pending создают неограниченный операционный долг. Истёкшая запись сохраняется в истории и аудите; продление/повторная подача — отдельное новое предложение. Никакая очистка истории не выполняется. |
| RepoPatch: код и документация | **Review допускается только для документационных профилей и разрешённых путей docs/README. Для кода общий Review не включать.** | Другие акторы не увидят непринятый патч, поэтому согласование кода через общую очередь создаёт ложную картину рабочего дерева. Код остаётся в текущем изолированном цикле правок и проверки. Автоприменение документации остаётся явной настройкой профиля, не глобальным поведением. |

### Уточнение границы проектного доступа для P2

Для строки «обычное человеческое право записи по проекту» используется существующая модель членства: любой участник проекта с ролью Owner, Admin или Member может создавать, просматривать и принимать/отклонять предложения по обычным целям. Owner/Admin проекта, Owner/Admin организации проекта и системный администратор также имеют доступ. Членство в организации с ролью Member без членства в конкретном проекте не даёт доступа к Inbox этого проекта. API-токен не считается человеком: он может только подать или отозвать собственное предложение при наличии ContextRead и валидной привязки к активной Actor-сессии.

## Обязательные инварианты реализации

1. Агент не принимает, не отклоняет и не редактирует статус чужого предложения. Эти операции доступны только человеку; для Decision/Constraint — только Owner/Admin.
2. Новое предложение привязано к проекту, задаче, подзадаче и активному Actor pipeline session. Идентификаторы автора, роли и профиля получаются на сервере, а не принимаются из payload.
3. При принятии проверяется `BaseRevision`. Несовпадение сохраняет статус `Conflicted`, не меняя целевое содержимое и не создавая ContentVersion.
4. Применение целевого изменения, новая ContentVersion, новый статус предложения и событие аудита сохраняются атомарно.
5. Откат принятого предложения создаёт новую ревизию через существующий ContentWriter; история не переписывается.
6. Повторный запрос принятия уже принятого предложения идемпотентен и возвращает сохранённый результат.
7. Содержимое предложения — недоверенные данные. Аудит содержит только allowlisted метаданные, но не Markdown, diff, payload, rationale, токены или пути с секретами.

## Границы фаз

- **P2:** модель и жизненный цикл Proposal, права, атомарное принятие/отклонение/отзыв/конфликт/истечение, аудит и API.
- **P3:** инструменты агента, их роль-профильный allowlist, пробуждение планера.
- **P4:** Inbox, diff/Markdown preview, пакетные операции и история в UI.
- **P5:** политика автопринятия по паре TargetKind × Operation. До завершения P5 всё кроме уже существующего безопасного создания ContextSection остаётся Manual.
- **P6:** RepoPatch. Не расширять его на код до отдельного решения об изолированном состоянии, видимом всем следующим акторам.

Эти решения не меняют уже согласованный контракт Markdown и не оборачивают повторно существующие Proposed Decision/Constraint или NeedsReview ContextSection: они уже являются reviewable drafts.

## Проверенный объём реализации и оставшийся контрактный долг

Проверка кода и тестов 10 ноября 2026 выявила ограничение, которое нельзя считать закрытым принятыми выше решениями:

- Revision-bound Proposal сейчас принимает только `ProposalOperation.Update`. `Create` и `Delete` отклоняются на доменном и Application-уровне; MCP `knowledge_propose` также явно принимает только Update.
- Это не ломает уже существующие create/review-потоки для `Decision` (`Proposed`), `Constraint` (`Proposed`) и `ContextSection` (`NeedsReview`): они остаются отдельными legacy review items в Inbox и намеренно не оборачиваются вторым Proposal.
- Для остальных целей универсальный revision-bound Create пока отсутствует. В частности, создание Milestone или Task через `knowledge_propose` сейчас невозможно.
- Revisioned Delete proposal тоже не реализован. Существующие человеческие удаления ContextSection, Milestone и Task записывают tombstone `ContentVersion`, но физически удаляют целевую строку. `RestoreContentVersionHandler` умеет восстановить выбранную предыдущую версию только пока целевая сущность существует; он не воссоздаёт удалённую строку. Поэтому удаление остаётся аудируемым, но не восстанавливаемым через текущий UI отката.

**Следствие для Definition of Done:** P2 и P1 нельзя объявлять полностью завершёнными относительно исходных разделов 4.2–4.5 и 5 только на основании зелёного CI. До merge нужно либо реализовать Create/Delete с безопасными tombstone/recreation semantics и тестами, либо отдельно утвердить сокращённый v1-контракт. Не расширять операции молча и не выдавать текущую историю удалений за полноценный rollback.
