# ProjectBeacon — Forward Plan (продолжение fix-plan.md)

Дата: 2026-09-28. База: HEAD `434cffb`. Формат шагов — как в `ProjectBeacon-fix-plan.md`
(`Проблема / Контекст / Меняем / Подшаги / Acceptance`), запуск через `agent-prompt-template.md`
с подстановкой `{STEP_NUMBER}` (для этого файла — `forward-plan`, шаги 1–10).

Все четыре 🔴-пункта fix-plan закрыты (песочница путей — коммит `4812798`, `WorkspacePath`).
Этот план закрывает расхождения между `design-doc-v2.md` и фактическим состоянием кода.

## Принципы неразрушения (читать перед любым шагом)

1. **Миграции EF — только additive.** Новая таблица или nullable-столбец — да.
   `ALTER COLUMN`, `RENAME`, `DROP` существующих сущностей — нет, если шаг явно не говорит иначе.
2. **DTO и контракты расширяются, не переписываются.** Новое поле — optional/nullable, в конец записи.
   Позиционные конструкторы существующих DTO не менять.
3. **Enum'ы только дополняются** (новые значения в конец, новые флаги). Не переименовывать и не удалять.
4. **Пункты, помеченные ✅ в roadmap-v2, не переписываются.** Новое поведение — новые файлы,
   новые методы, новые ветки с фолбэком на прежнее поведение.
5. **Существующие тесты не редактируются**, кроме случая, когда шаг сам меняет контракт.
   Новое поведение покрывается новыми тестами.
6. **Фолбэк обязателен.** Если новый источник данных недоступен (нет клиента, нет индекса, нет транскрипта) —
   система ведёт себя ровно как до шага.
7. В каждом шаге есть пункт **«Не трогать»** — файлы и механизмы, которые уже работают.

Общая валидация каждого шага: `dotnet build` 0 warnings/0 errors, `dotnet test` — без падений
существующих тестов; новые тесты из подшагов обязательны.

## 🔴 Приоритет 1 — доказательство центрального тезиса (design-doc §10)

Продукт утверждает: «скомпилированный бриф помогает агенту больше, чем самостоятельное исследование».
Сейчас это не измерено. Шаги 1–3 добавляют измерение, не меняя ни компиляцию брифа, ни пайплайн.

### Шаг 1. Сущность `EvalRun` и хранение прогонов

**Проблема.** Нет хранилища для пар «задача с брифом / без брифа → реальные токены, ходы, pass/fail».

**Контекст.** `ProjectBeacon.Domain/Entities/Projects/TaskItem.cs`, `ProjectBeacon.Infrastructure/Data/BeaconDbContext.cs`,
существующие миграции в `Infrastructure/Data/Migrations/`.

**Не трогать.** `CompileBriefHandler`, `PipelineHandlers`, `ClaimTaskHandler`, `FinishWorkCommand`.

**Меняем.**
- `Domain/Entities/Evals/EvalRun.cs`: `Id`, `ProjectId`, `TaskId`, `PairId` (связывает два прогона одной пары),
  `Condition` (`WithBrief` / `WithoutBrief`), `PromptTokens`, `CompletionTokens`, `TurnCount`, `Passed`,
  `StartedAt`, `CompletedAt`, `TranscriptRef` (ссылка на сырой лог, не сам текст).
- Enum `EvalCondition` — новый файл в `Domain/Enums/`.
- Регистрация в `BeaconDbContext` с теми же tenant-фильтрами, что у остальных project-scoped сущностей.
- Миграция `AddEvalRuns` — только `CREATE TABLE`.
- `Application/Evals/EvalHandlers.cs`: `RecordEvalRunHandler`, `ListEvalRunsHandler`.

**Подшаги.**
1. Сущность, enum, конфигурация EF, миграция.
2. Два хендлера + регистрация в `DependencyInjection.cs` (новыми строками).
3. Тесты: Domain (инварианты `EvalRun`), Application (запись и выборка), изоляция по тенанту
   (по образцу существующих `TenantIsolationPostgresTests`, новым файлом).

**Acceptance.** Миграция применяется на пустой и на заполненной БД без потери данных; старые тесты зелёные.

### Шаг 2. Реальный парный прогон

**Проблема.** Нужны настоящие числа из двух реальных прогонов агента, а не фикстуры.

**Контекст.** `Cli/Client/WorkstationActions.cs`, `Cli/Client/WorkstationDaemon.cs`,
`Application/Devices/DeviceHandlers.cs`, `Application/Agents/OpenCodeConnectionHandlers.cs`.

**Результат разведки (Шаг 2).** Клиент общается с `opencode serve` обычным HTTP на `127.0.0.1:4096`
(`ClientOpenCodeServe`): `POST /session`, `POST /session/{id}/prompt_async`, `GET /session/{id}/message`,
`POST /session/{id}/abort`, `GET /global/health`. Usage НЕ надо выдумывать: в ответе `GET /session/{id}/message`
у каждого сообщения уже есть `info.tokens = { input, output, reasoning, cache: { read, write } }` и `info.cost`.
Текущий `ListPartsAsync`/`ParseParts` этот эндпоинт уже вызывает и читает `info.role`/`info.id`, но выбрасывает
`info.tokens`/`info.cost` — значит расширение non-destructive: новый метод клиента суммирует `info.tokens`
по assistant-сообщениям. Чтение из `.opencode/data` не нужно.

**Не трогать.** Существующие действия `ListDir`, `InitProject`, `ApplyOpencode`, `ScanGguf`;
логику пуша OpenCode-конфига; `WorkspacePath`.

**Предварительная разведка (обязательна перед кодом).** Выяснить, каким способом клиент общается с запущенным
`opencode serve` и где доступна статистика токенов ответа. Результат записать в раздел «Контекст» шага.
Если у OpenCode нет API для отправки промпта с получением usage — шаг переформулировать
(например, чтение usage из `.opencode/data` после прогона) и не выдумывать интерфейс.

**Меняем.**
- Новое значение `RunEvalTurn` в конец enum команд рабочей станции.
- Новый метод в `WorkstationActions` (рядом, а не внутри существующих) с валидацией пути через `WorkspacePath`.
- `Application/Evals/EvalPairHandler.cs`: берёт бриф из `CompileBriefHandler` (только чтение), собирает два промпта
  (с брифом и без секции брифа — сборка локально в новом хендлере), ставит две команды, записывает две `EvalRun`.

**Подшаги.**
1. Разведка (см. выше), фиксация результата.
2. Enum + метод клиента + обработка результата на стороне API.
3. `EvalPairHandler`.
4. Тесты: клиентский метод на фейковом OpenCode-эндпоинте, хендлер на фейковой очереди команд.

**Acceptance.** На реальной задаче с online-девайсом появляются две `EvalRun` с разными реальными числами;
существующие тесты Pipeline/OpenCode/Devices без изменений.

### Шаг 3. Отчёт «context cost» на реальных данных

**Проблема.** В UI нет отчёта, который показывает не типизированные вручную числа.

**Контекст.** `Web/Features/Reports/`, существующий генератор отчётов, `API/Endpoints/`.

**Не трогать.** Существующие отчёты и их генератор.

**Меняем.**
- `GET /v1/reports/context-cost/{taskId}` — читает пары `EvalRun`, отдаёт сравнение (токены, ходы, pass/fail).
- Новый компонент в `Features/Reports/`, подключаемый в существующий экран как дочерний.
- Локализация через `IStringLocalizer<Web>` (resx), без английских строк в разметке.

**Acceptance.** Отчёт показывает данные из шага 2; при отсутствии пар — пустое состояние, а не ошибка.

## 🔴 Приоритет 2 — код-ориентация в брифе (design-doc §4)

### Шаг 4. Склейка `CodeIndex` с брифом на стороне клиента

**Проблема.** `CodeIndex` существует и работает (`GetTree`, `GetChangedScope`, `Search`, 448 строк, тесты),
и доступен агенту как MCP-инструменты. Но в скомпилированном брифе секции `tree_capsule` и `changed_scope` —
текстовые заглушки. Бриф компилируется на сервере, а рабочее дерево — на машине клиента.

**Контекст.** `Application/Context/CompileBriefHandler.cs` (строки с заглушками),
`Application/CodeIndex/CodeIndex.cs`, `Cli/McpStdioServer.cs`, `Cli/Mcp/McpApiTools.cs`.

**Не трогать.** `CodeIndex`, серверный `CompileBriefHandler` и его заглушки (остаются фолбэком),
токенайзер и бюджет.

**Предварительная разведка.** Найти точку, где клиентский MCP обрабатывает `context_compile` через `BeaconApiClient`
(в `McpStdioServer.cs` этого имени нет — вероятно, `McpApiTools.cs`).

**Меняем.** В клиентском слое после получения брифа подменять две заглушечные секции реальным выводом
`CodeIndex` (дерево с лимитом записей, changed-scope). Границу бюджета учитывать: секции остаются
«droppable», порядок секций сохраняется.

**Подшаги.**
1. Разведка, точка вставки.
2. Функция подмены секций (чистая, тестируемая без сети).
3. Подключение в обработчик `context_compile`.
4. Тесты: подмена при наличии репозитория; фолбэк на заглушки, если `CodeIndex` вернул ошибку или корень не git.

**Acceptance.** Бриф через клиентский MCP содержит реальное дерево и список изменённых файлов;
прямой серверный вызов возвращает прежние заглушки; старые compile-тесты без изменений.

## 🟡 Приоритет 3 — дисциплина агента (design-doc §5, §12)

### Шаг 5. Доставка правил `beacon-tool-discipline` и уточнение секции инструментов

**Проблема.** Правила «не утверждать, что инструмента нет, не вызвав его», «не заявлять визуальную проверку»
нигде не реализованы (имя встречается только в `design-doc-v2.md`). Секция `## Tools for this task` статична и
не называет инструменты индекса (`get_tree`, `search`, `get_changed_scope`).

**Контекст.** `Application/Context/CompileBriefHandler.cs`, `Application/Context/ExportAgentsMdHandler.cs`,
`Cli/Client/WorkstationActions.cs` (генерация opencode-конфига), `dotnet project docs/cold-diff-review.md`.

**Не трогать.** Логику `permission: deny`; принятое решение «Definition of Done живёт в constraint-системе,
а не в AGENTS.md».

**Предварительная разведка.** Выяснить, какой механизм OpenCode использовать для постоянных инструкций
(поле `instructions` в конфиге или файл правил) — не предполагать путь `.opencode/skills/`, пока не проверено.

**Меняем.**
- Текст правил — одна константа/ресурс в `Application`, версионируемая.
- Доставка: additive-запись в opencode-конфиг/файл инструкций при `ApplyOpencode` через проверенный механизм.
- В секцию `tools` брифа — добавить строки с именами инструментов индекса; существующие строки не менять.

**Acceptance.** После `ApplyOpencode` правила присутствуют в конфигурации агента; бриф называет инструменты индекса;
существующие тесты `WorkstationActionsTests` и compile-тесты проходят без правок.

### Шаг 6. Проверяемое подтверждение ревью в `finish_work`

**Проблема.** `ReviewerRun=true` — самозаявленный булев; это тот самый «непроверяемый claim», против которого
написан §12.

**Контекст.** `Application/Tasks/FinishWorkCommand.cs`, `Domain/Entities/Projects/TaskItem.cs`.

**Не трогать.** Текущее поведение при вызове без нового поля; pipeline-review (см. шаг 10 — решение фиксируется
документально, а не откатывается).

**Меняем.** Optional поле `ReviewTranscriptRef` в запросе. Если передано — хендлер проверяет, что по ссылке существует
отдельная запись изолированного прогона ревью (новая сущность `ReviewRun` или переиспользование `EvalRun` —
решение принять в разведке). Если не передано — прежняя логика.

**Acceptance.** Старые вызовы `finish_work` работают идентично; новый путь отвергает несуществующую ссылку.

## 🟡 Приоритет 4 — инфраструктура

### Шаг 7. `ProjectBeacon.Worker` (design-doc §3)

**Проблема.** Worker описан как одна из четырёх частей архитектуры, но проекта нет.

**Не трогать.** API, Web, Cli; они не должны зависеть от Worker in-process.

**Меняем.** Новый проект `ProjectBeacon.Worker` (Generic Host + `IHostedService`), подключение к тем же таблицам
через `BeaconDbContext`. Первые две задачи: очистка просроченных сессий/токенов; GitHub-sync с использованием
существующего boundary-aware матчера путей (без его переписывания). Additive-миграции при необходимости.

**Acceptance.** `dotnet build` всего решения зелёный; выключенный Worker не влияет на API/Web;
тесты Worker — отдельным проектом.

### Шаг 8. `FORCE ROW LEVEL SECURITY` как второй эшелон (design-doc §9)

**Проблема.** Изоляция тенантов держится только на EF-фильтрах; дизайн требует доказанной изоляции даже
для привилегированного пути приложения.

**Не трогать.** EF global filters (остаются основным механизмом), `TenantIsolationPostgresTests`.

**Меняем.** Raw-SQL миграция: `ENABLE` + `FORCE ROW LEVEL SECURITY` и политики, зеркалящие существующие
org/project-фильтры, для тех же таблиц. Разведка: как приложение передаёт tenant-контекст в сессию Postgres
(например, `SET LOCAL`) — политики строятся на нём.

**Acceptance.** Существующие тесты изоляции зелёные; новый тест — прямое SQL-соединение под ролью приложения
не видит чужие строки.

## ⚪ Приоритет 5 — верификация и документация (нулевой риск для кода)

### Шаг 9. Верификация Phase 7–9 (C0–C8, O1)

Пункты roadmap-v2 со статусом 🟡 «implemented, unverified» (device enroll, `init_project`, MCP-apply,
Solo/Pipeline модели, probe+install, client TUI, blue-green деплой) **не переписываются**. Для каждого — прогон
acceptance-критерия из roadmap на живом окружении (Playwright/Testcontainers). Расхождение оформляется отдельным
узким шагом-фиксом, а не переработкой. Итог — обновлённые статусы в roadmap.

### Шаг 10. `ProjectBeacon-design-doc-v3-delta.md`

Короткий документ, фиксирующий де-факто принятые решения, которых нет в v2:
- TOTP 2FA;
- OpenCode-подключения с пресетами и пуш конфига на клиент;
- Task Kinds с фазами; account-level модель чата;
- решение «pipeline review заменяет cold-diff gate для multi-agent задач; cold-diff-review остаётся требованием
  для одиночного `finish_work`» (либо противоположное решение — принять и записать явно);
- решение по §9: EF-фильтры как основной механизм + RLS как второй эшелон (после шага 8).

Правило: `design-doc-v2.md` не редактируется задним числом, изменения — только через delta.
